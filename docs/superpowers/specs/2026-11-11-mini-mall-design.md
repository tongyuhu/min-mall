## 1. 项目目的与已确认事项

用户学过 Java 和后端知识，但尚未完成实战。本项目用于系统学习，通过一套可在本地运行、可通过接口验证的商城，把工程组织、数据库、鉴权、缓存、事务、并发和外部服务对接串起来。

用户已确认：

- 单商家自营的实物商品商城，纯后端，同时提供买家端和管理端业务接口。
- 技术栈为 Java 21、Spring Boot 4、MyBatis-Plus、Redis、MySQL。
- 使用 Maven 多模块单体，最终只有一个 Spring Boot 应用启动入口。
- 支付和物流先采用本地模拟，保留真实服务接入接口。
- 本机已有 Java 21 和 Docker。只读检查确认 Java 为 21.0.2，Docker 客户端和引擎可访问。

本设计中其余具体业务规则和工程配置最初由设计者提出；用户已明确批准整份设计和默认范围。技术细节的实施选择见配套实施计划。

## 2. 目标、边界与交付标准

目标：实现商品上架、浏览、加购、结算、支付、发货、收货、售后退款的完整闭环；同时处理重复请求、库存不足、支付超时、重复通知和任务中断等情况。每个阶段都提供中文说明和可复现的接口操作示例。

第一版建议范围：

| 领域 | 交付内容 |
| --- | --- |
| 用户 | 用户名与密码注册登录、退出、查看和修改基础资料、修改密码、管理收货地址 |
| 商品 | 分类、品牌、SPU、SKU、规格、图片、价格、上下架、分页筛选、库存调整 |
| 购物车 | 添加、改数量、勾选、删除、失效商品提示 |
| 交易 | 结算预览、提交订单、订单列表与详情、取消、超时关闭、确认收货 |
| 支付 | 创建支付单、模拟支付成功或失败、异步通知、查单、退款、重复通知处理 |
| 履约 | 整单发货、运单、模拟物流轨迹、确认收货 |
| 售后 | 未发货整单退款、已发货整单退货退款、审核、退货寄回、收货验货、退款结果 |
| 营销 | 满减券、领券、有效期、使用门槛、订单占用与释放 |
| 管理 | 管理员登录、用户启停、角色权限、商品与库存管理、订单与售后管理、基础统计、操作日志 |
| 工程 | 数据库迁移、开发种子数据、OpenAPI、HTTP 请求示例、Docker Compose、配置说明、验证用例与学习文档 |

业务默认值：人民币，金额以分为单位；一个仓库；固定运费默认 0 元且可配置；一个订单只用一张满减券，不与其他优惠叠加；整单发货、整单退款，不拆单、不部分退款；售后申请期限为确认收货后 7 天，发货后未确认收货也可申请退货。

第一版不包含：前端页面、多商家入驻、结算分账、秒杀拼团、积分会员、商品评价、推荐算法、短信/社交登录、真实支付/物流账号接入、发票税务、多币种、多仓库、运费模板、换货、自动确认收货、生产环境上线。真实服务接入接口不代表已完成对应服务的认证、签名或上线验收。

避免以下结果：只有表的增删改查而没有交易闭环；用 Redis 锁代替数据库正确性；引入大量中间件却无法解释用途；只有正常流程、没有异常恢复；文档宣称通过了实际未执行的验证。

## 4. 技术基线与兼容性

- Java 21；Spring MVC；Maven Wrapper；统一父 POM 管理依赖；编译目标固定为 21。
- Spring Boot 4 稳定版本。实施计划阶段锁定具体发布版本，不使用 SNAPSHOT，不静默切换到 Boot 3。
- 使用 `mybatis-plus-spring-boot4-starter`，按需引入分页插件，不混入其他 MyBatis starter。
- MySQL 8.4 系列、Redis 7.4 系列作为建议基线；实施时锁定具体镜像版本，禁止使用浮动 `latest`。
- Spring Security 处理认证与授权；Redis 存储不透明登录令牌会话；密码使用 BCrypt。第一版不额外引入 JWT 刷新机制。
- Flyway 管理数据库版本；Spring Validation 校验请求；OpenAPI 描述接口，文档组件选用明确支持 Boot 4 的版本。
- JUnit 和 Spring Boot 测试支持编写验证用例；数据库并发验证使用真实 MySQL，不能以 H2 的结果替代。
- 依赖版本的精确组合和 Maven 下载验证属于实施计划/实现工作；本设计只确认官方存在兼容路径，未宣称依赖已解析或项目可编译。

核对依据（2026-11-11）：[Spring Boot 官方系统要求](https://docs.spring.io/spring-boot/system-requirements.html)列出的 Java 支持范围包含 Java 21；[MyBatis-Plus 官方安装文档](https://baomidou.com/getting-started/install/)提供 Boot 4 专用 starter，并注明从 3.5.13 起支持。具体依赖应使用实施时核验的稳定发布版。

## 5. 工程结构与依赖规则

建议父工程 `mini-mall`，包名前缀 `com.minimall`。模块内按业务组织 `api`、`application`、`domain`、`infrastructure` 等包；简单功能可合并层次，不为每个实体强行创建接口与实现类。

| Maven 模块 | 职责 | 允许依赖的内部模块 |
| --- | --- | --- |
| `mall-common` | 错误码、分页、当前身份契约、时间抽象、基础技术配置；不包含业务实体 | 无 |
| `mall-user` | 买家账户、地址、用户状态、买家认证数据查询 | common |
| `mall-catalog` | 分类、品牌、商品、规格、库存与库存流水 | common |
| `mall-marketing` | 优惠券模板、领取记录、优惠试算、占用和核销 | common |
| `mall-trade` | 购物车、订单、支付、物流、售后与后台恢复任务 | common、user、catalog、marketing |
| `mall-admin` | 管理员、RBAC、审计日志、管理统计与管理端接口 | common、user、catalog、marketing、trade |
| `mall-app` | 唯一启动入口、配置装配、认证过滤链、任务启停和运行资源 | 其余模块 |

依赖方向禁止成环。业务模块暴露应用服务或门面与专用 DTO；禁止跨模块调用 Mapper、直接修改对方表、暴露数据库实体作为外部 API。`mall-trade` 编排订单事务，调用商品和营销模块服务，共享同一个数据源与事务管理器。

用户与管理员的认证查询分别由所属模块实现，认证基础设施通过 common 中的契约在 app 中装配；user、trade 不反向依赖 admin。管理员角色不等同于买家身份，两类会话隔离。

支付和物流暂作为 trade 内的独立业务包，通过 `PaymentGateway`、`ShippingGateway` 接口与模拟适配器隔离。退款、发货等领域规则放在应用服务，避免未来更换渠道时重写订单规则。第一版无需为每个外部接口另建 Maven 模块。

## 6. 数据模型与统一约定

| 所属模块 | 主要表及用途 |
| --- | --- |
| user | `member`、`member_address` |
| catalog | `category`、`brand`、`product_spu`、`product_sku`、`product_image`、`specification`、`specification_value`、`sku_spec_value`、`sku_stock`、`stock_log` |
| marketing | `coupon_template`、`member_coupon`、`coupon_log` |
| trade | `cart_item`、`trade_order`、`order_item`、`order_address`、`order_status_log`、`payment_order`、`payment_notification`、`shipment`、`shipment_track`、`after_sale`、`after_sale_log`、`refund_order`、`integration_task`、`mock_payment_transaction`、`mock_refund_transaction` |
| admin | `admin_account`、`admin_role`、`admin_permission`、`admin_account_role`、`admin_role_permission`、`admin_operation_log` |

`integration_task` 是数据库中的持久化对接任务，不是新增中间件；保存支付/退款/物流命令及模拟通知的待处理状态、重试次数、下次执行时间、租约和最后错误。

数据约定：

- 主键使用 MySQL BIGINT；对外 ID 序列化为字符串；订单号、支付号、退款号独立且唯一。
- 金额使用 BIGINT 分，Java 使用 long 并检查溢出；不使用浮点数。数量为正整数，并限制单次购买数量和分页大小。
- 时间由可注入的时钟提供，统一存 UTC，接口使用带时区的 ISO 8601；展示示例采用北京时间。
- 使用 InnoDB、utf8mb4；名称和搜索字段设长度限制。状态变更以条件更新或行锁确保并发正确。
- 下单保存商品名称、SKU 规格、图片、成交价、优惠分摊和地址快照；后续商品或地址修改不影响历史订单。
- 订单及资金记录不硬删除；商品以下架/归档处理，已有订单仍可查询；用户名第一版不回收。
- 关键唯一约束：用户名、购物车用户与 SKU、用户与下单幂等键、订单支付单、渠道交易号、渠道通知号、退款业务号、订单运单、库存变更业务键。
- 优惠券按模板与用户唯一领取；库存、优惠券状态、订单状态的索引支持后台扫描。详细字段、索引与外键策略由实施计划展开。

## 7. 用户、权限与接口规范

买家路由使用 `/api/v1/**`，管理路由使用 `/admin/v1/**`，支付通知使用 `/callbacks/v1/**`，开发模拟控制使用 `/dev/v1/**`。

注册采用用户名和密码，不要求手机或邮箱验证。买家初始状态正常；禁用账号和修改密码时撤销相关会话。会话使用随机高熵 Bearer Token，Redis 只保存令牌摘要索引及身份数据，默认有效期 2 小时，不做滑动续期；退出删除当前会话。Redis 不可用时受保护接口明确失败，禁止放行。

买家与管理员分别登录；每次操作同时检查接口权限和资源归属，不能仅凭 URL 中的 ID 查询他人订单或地址。管理员初设超级管理员、运营、客服三个角色，权限细化到商品管理、发货、退款审核、用户管理等动作；角色权限修改对后续请求生效，不把过期权限长期写死在会话中。

接口使用统一错误结构、业务错误码、请求追踪 ID，并保留正确 HTTP 状态码。分页统一 `page`、`size`，最大 100；排序字段使用白名单。创建订单等关键写操作接收 `Idempotency-Key`；相同身份、相同键和相同内容返回原结果，不同内容使用同键返回冲突。

商品查询公开；购物车、订单、优惠券和地址需买家身份；管理功能需管理员权限。回调依赖渠道签名校验而不是买家令牌。模拟管理接口仅在显式启用的 local/test 配置下注册，并校验开发密钥，其他环境不注册相关路由。

商品图片第一版保存外部图片 URL，不提供文件上传和对象存储；后端不主动抓取 URL。日志不记录明文密码、完整令牌、完整地址或渠道密钥；关键管理动作记录操作者、目标、结果和时间。

## 8. 商品、购物车与优惠券规则

SPU 表示商品，SKU 表示具体规格组合；无规格商品也有一个默认 SKU。同一 SPU 内规格组合唯一。上架要求商品有效且存在可售 SKU；SKU 价格和库存更新保留记录。查询支持分类、品牌、价格范围和关键词，关键词使用 MySQL 条件查询，第一版不承诺全文搜索能力。

购物车数据存 MySQL，Redis 不作为购物车唯一存储。加购时校验商品存在和数量上限；结算时重新查询上下架、价格和库存，不承诺加购时的价格和库存。

优惠券仅支持全场满减，门槛按商品小计计算，不含运费；一单一券且不叠加，优惠不超过商品小计。模板发放总量和每用户一次的领取限制由数据库原子更新和唯一约束保证。

券状态：可用、已占用、已使用、已失效。下单时占用，支付成功核销，未支付取消时释放；释放时如已过期则转为失效。退款后不返券。券在有效期内已被订单占用，允许在该订单支付截止时间前完成支付，即使期间模板到期。禁用模板阻止新的领取和使用，已有占用保留。

优惠按行金额比例分摊到订单项，使用整数运算并以固定顺序分配尾差，保证订单项金额总和等于订单商品实付总额。退款第一版按整单实付金额处理。

## 9. 下单、库存与订单状态

订单主状态：`PENDING_PAYMENT`（待支付）、`PAID`（待发货）、`SHIPPED`（已发货）、`COMPLETED`（已收货）、`CLOSED`（未支付关闭）、`REFUNDED`（整单退款完成）。售后和支付状态独立保存，不把所有组合塞进订单主状态。

下单过程：

1. 读取买家地址、商品和优惠券，服务端计算最终金额。预览结果只作展示，提交时重新校验；价格变化返回需重新确认的冲突，不能悄悄按新价格扣款。
2. 按统一资源顺序加锁：同一订单相关操作先锁订单；多 SKU 按 SKU ID 升序锁库存；随后处理优惠券。所有路径保持同一顺序，避免死锁放大。
3. 在一个 MySQL 本地事务中创建订单及快照、扣减可售库存、增加占用库存、记录流水并占用优惠券；任一步失败整体回滚。
4. 下单幂等键写入订单并受唯一约束保护，重复请求返回同一订单。清理本次购买对应购物车项与订单创建一并提交。

库存分为可售数量与占用数量。下单只在可售数量足够时转入占用；支付成功从占用中扣除，表示售出；未支付取消从占用归还可售；退款归还规则见售后章节。管理端调整只允许调整可售数量，不得把已占用库存直接覆盖掉。库存变化与业务流水同事务，流水业务键唯一，重试不得重复释放或扣减。

待支付订单默认 30 分钟到期。关闭任务按数据库截止时间扫描，只有仍处于待支付状态且未发生渠道成功收款时才关闭。用户取消和超时关闭共用状态校验及释放逻辑。支付与取消/关闭竞争时，依赖同一订单行锁及状态条件决定结果，而不只依赖 Redis 锁。

第一版保留单订单单支付单，允许未成功的支付单重复获取支付参数，渠道请求使用同一支付业务号。订单禁止修改已保存的商品、金额和地址；需要变化时取消后重新下单。

## 10. 支付模拟与异常恢复

`PaymentGateway` 支持发起支付、查询支付、关闭支付、发起退款、查询退款，以及通知验签和解析。实际网络调用必须在数据库事务之外；业务状态与待执行对接任务在同一事务落库，由工作任务执行调用并用条件更新记录结果。

模拟渠道同样保存自己的支付和退款记录，不能直接修改商城订单。开发接口让模拟渠道进入成功或失败状态，并产生持久化通知任务；通知经正常业务处理入口推进订单。支持重复通知、延迟通知、暂时失败和重试演示，普通买家接口不能自报支付成功。

通知处理校验签名、商户标识、支付号、渠道交易号、币种和金额；通知记录和支付状态使用唯一约束及状态条件去重。成功通知在同一事务内更新支付单、订单、库存占用和优惠券；事务提交后才返回成功应答。失败或不合法通知不得推进订单。

支付任务重试使用稳定业务号保证渠道幂等。调用超时表示结果未知，先查单再决定后续动作，不能直接标记失败。支付失败允许同一有效支付单再次尝试；已成功或已关闭状态不可倒退。

支付是否及时，以验签后可信的渠道实际收款时间为准，收款时间不晚于订单支付截止时间才算期限内付款；保存该时间用于查单、通知和补偿的一致判断。模拟渠道使用同一可注入时钟。收款时间缺失或矛盾时先查单，仍无法确定则保留待处理并告警，不猜测成功或释放库存。

用户取消/到期关闭前先查询并关闭渠道支付；渠道已在期限内收款且本地仍待支付，则按支付成功处理，即使通知到达时已过截止时间；渠道状态未知时保留待支付并重试，不先释放库存。若渠道实际收款晚于截止时间，即使本地尚未关闭，也必须在同一事务内关闭订单、释放占用库存和优惠券、记录异常收款及全额自动退款任务，不进入履约。若本地已关闭仍收到成功通知，无论渠道收款时间如何，都不重新激活订单、不重新扣库存：记录异常收款，创建全额自动退款任务，保持订单关闭并保留退款可查询记录。自动退款任务使用唯一业务键，避免通知与查单重复触发退款。

零元订单由下单事务直接转为已支付，记录零元结算信息、完成库存占用扣除与券核销，不调用渠道。退款时同样记录零元退款结果。

## 11. 履约与售后

仅已支付且无进行中售后的订单可以发货；一个订单一张运单，订单状态、运单创建和待调用物流任务同事务提交。调用物流失败保留可恢复任务，不重复产生运单。物流接口支持创建运单、查询轨迹；模拟渠道使用固定业务号并支持幂等重试。

买家只能对自己的已发货订单确认收货；正常确认收货转为已完成。物流显示已签收与用户确认收货分开记录。第一版不自动确认收货。

售后申请类型：

- 待发货订单：申请整单仅退款，管理员同意后提交退款。
- 已发货/已收货订单：申请整单退货退款，审核同意后由买家填退货运单；管理员确认收到且验货通过后提交退款。已收货订单需在 7 天内申请。

售后状态包括待审核、已拒绝、待退货、待验货、退款中、已完成、已撤销。拒绝或退款前撤销后可在有效条件下重新申请，同一订单同时最多一个有效售后。进入退款中后不能由买家撤销。退款失败保持可重试并在后台展示原因，不伪装成已完成。

售后申请、发货和确认收货在同一订单锁下互斥；进行中售后暂停发货及确认收货。未发货整单退款成功时归还库存一次；已发货订单只有管理员验收退货后才允许退款和归还库存，单独记录验收与归还事件并去重。自动退款的已关闭订单已释放库存，不再次归还。退款成功后订单转为已退款；优惠券不返还。

默认整单退款含原实际支付的运费，退货运费由用户承担且不进入系统计算；损坏拒收、争议仲裁、部分商品验收和换货不属于第一版。

## 12. Redis、任务、缓存与故障处理

Redis 用于登录会话、登录频率限制、商品详情短期缓存；库存与订单金额以 MySQL 为准。商品缓存失效后可回源，Redis 故障时商品读取可回源，但鉴权和登录限流不得静默绕过。

缓存使用带随机抖动的 TTL，空结果短期缓存；商品更新在数据库提交后删除对应缓存。接受短期展示陈旧，结算必须读取数据库并确认价格。第一版不承诺缓存与数据库强一致，也不依赖缓存判断可售库存。

定时任务负责订单关闭、通知投递、对接重试、退款查单和异常支付补偿。任务按 `next_run_at` 扫描，通过数据库状态、租约和条件更新领取；进程崩溃后租约到期可重新领取。单应用即可运行，同时要能抵御任务重入；不能仅依赖内存队列或 Redis 过期通知。

重试采用有限退避；达到上限后转为需人工处理并保留原因，后台提供查阅与受权限控制的重试接口。人工重试仍使用原业务号和幂等约束。非成功的退款与对接任务不得因为超出重试次数而从列表消失。

## 13. 本地运行、配置与可观测性

- Docker Compose 默认只启动 MySQL 和 Redis，应用在本机 IDE/Maven 中运行；另提供可选应用容器配置和 Dockerfile，用户需要时再构建。
- 数据卷持久化，提供健康检查和独立开发凭据，通过环境变量配置连接信息；不删除已有容器和数据卷，不默认占用已有服务端口。
- Flyway 版本迁移为表结构唯一来源；开发种子数据使用独立 local 配置，提供商品、SKU、优惠券和演示账号。管理员初始密码由本地环境变量注入，说明文档提供初始化方法。
- 环境配置区分 local/test/prod；local 模拟功能需显式开启；prod 缺少真实渠道配置时启动失败或拒绝对应能力，不回退为模拟支付。
- 日志包含请求追踪 ID、业务号与关键状态变化；提供受限健康检查，不公开凭据或完整运行环境。
- README 提供 Windows PowerShell 命令、环境变量、启动顺序、常见故障、重置演示数据方式；破坏性重置必须显式执行，不能作为正常启动步骤。

## 14. 验证策略与验收条件

当前遵循用户既有偏好：未明确授权前不编译、不打包、不运行会触发编译的测试。设计审核不构成编译或启动服务的授权。实现时可编写测试，先执行不编译的静态检查；实际运行验证需明确记录是否获得授权及是否执行。

需要准备的验证内容：

- 规则测试：金额计算与尾差、优惠门槛与过期、订单状态、退款资格与时间边界。
- MySQL 集成测试：并发购买不能超卖；多 SKU 失败全部回滚；取消与支付竞争；重复回调不重复核销；重复退款不重复返库；相同幂等键不同请求内容被拒绝。
- 恢复测试：支付调用结果未知、期限内收款但通知晚到、期限后收款且本地尚未关闭、已关闭订单迟到成功、渠道收款时间未知、任务领取后崩溃、退款重试、Redis 不可用时鉴权拒绝和商品回源。
- 权限测试：买家不能读取他人订单，运营不能修改管理员权限，非 local/test 下没有模拟控制接口。
- 端到端接口脚本：注册登录、管理端上架、加购领券、下单模拟付款、发货收货、退货退款；另附超时关闭和库存竞争演示。

完整交付需包含源代码、数据库迁移、开发数据、配置示例、接口定义、可重复执行的请求示例、关键测试代码、中文学习文档和验证记录。只有在获得运行授权并执行相应验证后，才能宣称可启动、测试通过或闭环验证成功；未执行部分明确列出，不以静态检查代替运行结论。
