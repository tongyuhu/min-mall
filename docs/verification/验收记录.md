## 本轮改动步骤

1. **核对环境并首次运行完整 verify。** 确认 Java 21、Docker 可用，三个本地端口空闲；业务代码编译成功。测试编译发现 `assertEquals(long, tx.execute(...))` 的泛型与 JUnit 重载冲突，改成先接收明确的 long 变量，再断言。
2. **启动独立本地基础服务。** 创建本项目 `.env` 随机凭证，只启动 mini-mall 的 MySQL、Redis，保留其他项目环境；启动应用执行 14 个迁移及本地种子初始化。
3. **定位时间写入根因。** 第一轮完整集成测试出现优惠券不可领取、过期扫描未命中、物流重放时间不一致，共 5 个失败。新增 PersistenceTimeIT，修正前明确得到：期望 `05:00:00.123456Z`，实际 `13:00:00.123457Z`，同时复现 8 小时时区偏移和微秒四舍五入。
4. **统一 UTC 与微秒存储。** Database 将 Instant 明确转换为 UTC LocalDateTime，并在写入 DATETIME(6) 前截断到微秒；测试中直接更新到期时间和租约的 JDBC 参数也使用 UTC LocalDateTime。没有改变数据库已有迁移、放宽业务断言或把失败用例跳过。
5. **修正运行配置。** 增加 `.mvn/jvm.config` 固定 UTF-8，消除中文编译诊断乱码；关闭不使用的默认 UserDetailsService 自动配置，避免生成无用的默认登录密码。文档补充 Windows 重新打包前先停应用、PowerShell 带点号 Maven 参数加引号的要求。
6. **重新运行完整 verify。** 停止占用 JAR 的本次应用进程后重新打包，获得 59/59 通过，包括审阅修正对应的并发、权限、金额、失败支付、租约、退款恢复和 HTTP 错误边界用例。
7. **修正 smoke 的 PowerShell 数组筛选。** 首次 smoke 实际已完成退款，但 `Invoke-RestMethod` 将数组作为单个管道对象输出，导致券状态筛选为空。用独立数组样例复现后，改成先接收数组再逐项筛选；第二次 smoke 全部断言通过。
8. **验证真实进程重启恢复。** 通过 HTTP 创建已付款订单和 PENDING 退款，核对 PID 命令行后终止本次 Java 进程，重启同一应用，再确认渠道到账；验证原退款号完成、没有重复退款、库存只恢复一次。
9. **整理交付。** 更新 README、学习说明、代码审阅状态、测试结果汇总及本记录，最终静态检查后提交。保持本地应用和基础服务运行；没有合并或推送分支。

时间处理依据：[MySQL Connector/J 时间类型处理文档](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-datetime-types-processing.html)。DATETIME 本身没有时区，不能把 JDBC Timestamp 的默认转换等同于明确保存 UTC。
