## 第一遍：跑通正常交易

1. 按 README 配好环境，确认启动迁移成功，检查健康接口。
2. 使用 HTTP 文件自己创建买家、地址、分类、商品与库存，观察每步新增的数据。
3. 领取满 30 减 5 的券，买两件 19.90 元商品。核对商品 3980 分、优惠 500 分、应付 3480 分（默认免运费）。
4. 试算之后改价格，验证旧摘要被拒绝；重新试算、下单，再重复同一个幂等键，确认返回同一订单。
5. 模拟付款、发货、收货、退货验收、退款。逐步检查库存从可售→占用→扣减→返库，券从 AVAILABLE→RESERVED→USED。

## 第二遍：主动制造故障

现在也可以通过真实页面学习：[07-前端全链路](07-前端全链路.md)。从商品详情到购物车、结算、支付，再切换管理后台发货、审核售后，把页面、API、应用服务和 SQL 串起来。

每次只改变一个变量，先写出自己的预测，再观察状态与流水。

- 下单中途库存不足：事务是否留下订单、库存占用或券占用？
- 回调发送两遍、延迟一分钟、先失败一次：支付是否只确认一次？
- 取消时渠道已经收款：是否错误关单返库？已关闭后才收到异常收款如何退款？
- 退款一直 PENDING 或明确 FAILED：任务是等待还是退避，何时需要人工处理？
- 进程在渠道成功、本地未提交时退出：同一 refundNo 再查单能否恢复？
- Redis 故障：认证应拒绝，商品缓存能否回源？
- 管理员或会员令牌访问另一方 API、访问别人地址或订单：是否被拒绝？

## 代码中的取舍

普通实体操作使用 MyBatis-Plus。条件更新、锁和流水 SQL 通过公共 Database/SqlMapper 预编译参数执行，SQL 必须由所属模块在代码中构造，客户端不得传 SQL；复杂条件仍集中在 Repository，便于观察事务和索引。这样少一些转发 Mapper，但需要持续检查模块边界与 SQL 参数。

商品缓存仅用于展示；下单从数据库重新读取并锁定。任务表与业务数据在同一事务提交，渠道调用在事务外进行，再在新事务内合并结果。幂等由数据库唯一键和业务号保证，Redis 不承担库存事实或资金事实。

学习项目优先让状态和恢复路径可见，暂不增加分布式架构。当前默认全额退款且不返券；若以后扩展部分退款，必须重新设计按订单项的退款金额、尾差、库存和券规则，不能只在 DTO 上加一个 amount 字段。
